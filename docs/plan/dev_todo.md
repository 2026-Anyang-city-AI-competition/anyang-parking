## 1. 조사 결과 데이터셋

### 1.1 원칙

아래 세 시간은 절대 같은 값으로 취급하지 않는다.

1. **출입 가능시간**: 일반 시간제 차량이 실제로 들어가고 나올 수 있는 시간
2. **요금 징수시간**: 주차요금이 계산되는 시간. 이 시간이 끝나도 무료 개방일 수 있다.
3. **예측 가능시간**: 실시간 데이터가 정상적으로 움직이고 검증되어 AI 예측을 제공할 수 있는 시간

`reports/태영.txt`는 조사 메모로 보존하고, 서비스는 메모 문장을 직접 파싱하지 않는다. 검증한 결과를 아래 CSV로 옮긴 뒤 스키마 검증을 통과한 값만 사용한다.

### 1.2 정본 파일

신규 생성 예정:

- `data/raw/parking_access_rules.csv`: 조사로 확인한 출입·과금 규칙. **주차장 × 요일그룹 267행. 서비스 정본.**
- `data/processed/prediction_availability.csv`: DB 진단으로 산출한 예측 가능시간
- `data/processed/parking_access_rules.csv`: **분석용 별도 파일.** 주차장 1행 89행이며
  `feed_status`·`enterable_status`를 담는다. A20/A22가 읽는다. 서비스 경로는 이 파일을 읽지 않는다.

서비스본과 분석본은 **합치지 않는다.** `scripts/crosscheck_access_rules.py`가 대조만 하고
충돌·보강 후보·양쪽 미확인을 보고한다. 현재 충돌 0건, 일치 189행, 양쪽 미확인 26곳이다.

`parking_access_rules.csv`는 **주차장 × 요일그룹 한 행**으로 저장한다.

| 필드 | 예시 | 의미 |
|---|---|---|
| `parking_id` | `39` | `parking.db.lots.parking_id` |
| `name` | `안양7동노외` | 검수용 이름. 조인은 ID로만 한다. |
| `day_group` | `weekday` | `weekday`, `saturday`, `sunday_holiday` |

| `exit_windows` | `00:00-24:00` | 출차 가능 구간 |
| `fee_windows` | `09:00-17:00` | 과금 구간. 종일 무료면 빈 값 |
| `fee_mode` | `paid_window_free_outside` | 과금 정책 코드 |

| `access_status` | `confirmed_open` | `confirmed_open`, `confirmed_restricted`, `unknown` |
| `general_public` | `true` | 일반 시간제 승용차 이용 가능 여부 |

| `effective_to` | 빈 값 | 임시 운영 종료일. 미정이면 빈 값 |
| `checked_at` | `2026-09-15` | 확인일 |
| `evidence_method` | `official_web` | `official_web`, `phone`, `field`, `user_experience` |
| `evidence_ref` | URL/사진/기관명 | 재검증 가능한 근거 |
| `note` | `17시 이후 무료 개방` | 예외·주의사항 |

시간 표기 규칙:

- 24시간은 `00:00-24:00`으로 쓴다.
- `00:00-00:00`을 24시간 또는 휴무로 추정하지 않는다.
- 확인할 수 없으면 시간값을 비우고 `access_status=unknown`으로 둔다.
- 자정을 넘는 구간은 `22:00-24:00|00:00-06:00`처럼 명시한다.
- 여러 출처가 충돌하면 확정값을 만들지 않고 `unknown`으로 돌린다.
- 운영시간만 보고 출입 가능시간을 복사하지 않는다.

## 2. 추천 가능 여부 판정 — P0

### 2.1 판정식

```text
주차장 도착시각 = 사용자 출발시각 + 차량 ETA
예상 출차시각   = 주차장 도착시각 + 사용자가 입력한 주차시간
```

다음 조건을 모두 만족해야 추천 순위에 넣는다.

1. 일반 시간제 차량이 이용 가능한 주차장이다.
2. 도착시각이 입차 가능구간 안이다.
3. 예상 출차시각이 출차 가능구간 안이다.
4. 주차 구간이 폐쇄시간을 건너면 `overnight_allowed=true`로 확인되어 있다.
5. 임시폐쇄·월정기 전용·차종 제한에 걸리지 않는다.

`access_status=confirmed_restricted`만 강제 제외에 사용한다. `unknown`을 24시간 개방으로 간주하지 않으며, 결과에는 미확인 경고를 표시한다.

### 2.2 추천 파이프라인 변경

```text
후보 조회
→ 차량 ETA 계산
→ 도착·예상 출차시각 계산
→ 출입 규칙 검사
→ 이용 불가 후보 제외
→ 가능한 후보만 예측·요금 계산
→ full_prob 강등
→ 도보순/요금순 반환
```

제외 후 후보가 `minimum_candidates`보다 적으면 반경을 단계적으로 넓혀 다시 검사한다. 최종적으로 부족하면 없는 후보를 채워 넣지 않고 부족 사유를 반환한다.

### 2.3 응답 규격

추천 순위에서 제외한 항목은 `excluded` 배열로 분리한다. 기존 `unavailable`은 실시간 미제공 카드와 의미가 겹치므로 역할을 명확히 나눈다.

```json
{
  "excluded": [
    {
      "parking_id": 7,
      "name": "안양2동노외",
      "reason": "closes_before_departure",
      "arrival_at": "20:00",
      "expected_departure_at": "00:00",
      "access_closes_at": "22:00",
      "message": "예상 출차 전에 주차장이 폐쇄돼요."
    }
  ]
}
```

사유 코드:

- `entry_closed_at_arrival`
- `closes_before_departure`
- `closed_interval_crossed`
- `general_public_not_allowed`
- `temporary_closure`
- `vehicle_restriction`
- `access_schedule_unknown`
- `insufficient_exit_margin`

3단계 구현: `src/serve/access_check.py`의 `check_access()`는 `AccessDecision`을 반환한다.
`available=true`는 이용 가능, `false`는 확인된 이용 불가, `null`은 미확인이다.
미확인은 `excluded=false`로 반환하며 24시간 개방으로 확정하지 않는다.
4단계 연결 완료: 추천 요청마다 CSV 변경을 확인하고, 이용 불가 후보는 `excluded`에 분리한다.
제외 후 최소 후보가 부족하면 1→2→3km로 확대하며 기존 차량 ETA는 재사용한다.
미확인 후보는 경고와 함께 유지하고 고정 피드는 최소 추천 후보 수에 포함하지 않는다.

### 2.6 출발시각·주차시간 선택과 시각 계산 — P0

사용자는 고정된 `지금 출발/30분 뒤`와 `30분/1시간/2시간/3시간`만 고르는 방식이 아니라,
다음 값을 **5분 단위**로 선택한다.

- 출발시각: 기본값은 지금이며 `+5분` 단위로 변경한다. 날짜·시·분 선택 바텀시트를 제공한다.
- 주차시간: 빠른 선택 버튼과 별도로 5분 단위 직접 설정을 제공한다.
- 출발지: HTTPS에서 현재 위치를 기본으로 받고, 위치 권한 거부 시 주소·장소 직접 입력을 제공한다.
- 도보시간은 주차 완료 후의 시간이므로 AI 예측시각과 요금 시작시각에 더하지 않는다.

후보마다 차량 ETA가 다르므로 아래 계산을 **주차장별로 각각** 수행한다.

```text
사용자 출발시각       = 현재시각 + 출발 지연시간
주차장 도착시각       = 사용자 출발시각 + 해당 주차장 차량 ETA
AI 예측시각           = 주차장 도착시각
예상 출차시각         = 주차장 도착시각 + 선택한 주차시간
요금·출입 판정 구간  = [주차장 도착시각, 예상 출차시각]
```

현재 서비스 predictor의 지원 범위는 최대 120분이다. A23의 120분 초과 결과는 아직 `partial`이라
제품에 노출하지 않는다. 5분 단위 입력값은 가장 가까운 서비스 horizon으로
계산하되 실제 사용한 `model_horizon_min`을 응답에 남긴다. 120분을 넘는 도착시각은 출입·요금은
계산하지만, 별도 장기모델이 검증되기 전까지 AI 수치를 숨기고 `unsupported_horizon`을 표시한다.

- [x] 프런트 출발시각 바텀시트: 지금~120분을 5분 단위로 선택
- [x] 프런트 주차시간 바텀시트: 빠른 선택 + 5분 단위 직접 설정

- [x] 미래 출발도 공통 ETA 하나가 아니라 후보별 ETA를 사용 — 현재 교통 기준임을 카드 응답에 표시

## 4. 요금 API와 계산기 보강 — P0

현재 추천 API 안에서 요금을 계산하지만, UI에서 시간·할인만 바꿔 빠르게 다시 계산할 수 있도록 독립 견적 API를 추가한다.

### 4.1 `POST /api/v1/fare/quote`

요청 예시:

```json
{
  "parking_id": 39,
  "arrival_at": "2026-09-15T16:00:00+09:00",
  "parking_minutes": 240,
  "benefit_codes": []
}
```

응답 예시:

```json
{
  "parking_id": 39,
  "arrival_at": "2026-09-15T16:00:00+09:00",
  "expected_departure_at": "2026-09-15T20:00:00+09:00",
  "access": {"available": true, "status": "confirmed_open"},
  "fare": {
    "billable_minutes": 60,
    "free_minutes_outside_fee_window": 180,
    "payg": 1000,
    "daily_pass": 7000,
    "recommended_option": "payg",
    "saving": 6000,
    "applied_benefit": null,
    "breakdown": []
  }
}
```

7단계 구현 완료: `src/serve/fare_quote.py`의 `quote_fare()`가 추천을 다시 돌리지 않고
`parking_id`·도착시각·주차시간·감면 코드만으로 견적을 만든다. 추천과 같은 `calc_fare`와
`check_access`를 쓰므로 두 경로의 금액이 어긋나지 않는다. 출입 판정은 요금 계산을 막지 않는다 —
이용 불가여도 참고 요금을 돌려주고 `access.available=false`로 알린다.
`benefit_codes`는 지금 0~1개만 받는다. 중복 감면은 조례 확인 전까지 곱하지 않고
`multiple_benefits_unsupported`(422)로 거절한다 — 10단계에서 항목별 계산으로 바꾼다.
일일권은 `recommended_option`·`saving`으로 병기만 하고 `daily_pass_purchasable`은 null이다.

### 4.2 계산 보강

6단계 연결 완료: 추천 카드의 `fare`에 계산 내역·유료분·무료분·날짜별
`fee_schedule`과 `fee_source`를 반환한다. 조사 요금 미확정·누락 시 기존 DB 시간으로
계산하되 `legacy_db_unverified`, 일부 날짜만 확정이면 `mixed`로 표시한다.
**하루를 넘는 주차 (해석 확정)**

비고 10의 25,000원은 「일 최대요금」이므로 **날짜마다** 건다. 그래서 유료분을 날짜별로 나눠
각 날에 누진을 적용하고 각 날에 상한을 건 뒤 합산한다. 여러 날을 한 줄로 이어 누진하면
마지막 구간 단가(1급지 10분 1,200원)가 계속 붙어 과다청구가 된다. 하루짜리 주차의 결과는
바뀌지 않는다 — 날짜가 하나면 기존 계산과 동일하다.

⚠️ 조례가 「하루를 넘는 주차에서 누진 구간이 날짜마다 초기화되는지」를 명시하지 않는다.
날짜별 초기화로 해석했고, 이쪽이 사용자에게 더 싸다. 안양시 확인이 필요한 항목이다.

**일일권 이용 범위 (해석 확정)**

별표 5가 값을 「운영시간 × 급지」로 정하므로, 일일권은 **입차 당일의 유료시간**을 사는
상품으로 본다. 유료 날짜가 N일이면 N장이 필요하다고 세어 `daily_pass_days_required`로 준다.
다만 연장·재구매가 가능한지는 확인된 바 없어 **N>1이면 선불 총액을 제시하지 않고**
`prepaid_reason`으로 사유를 준다. `daily_pass_purchasable`은 여전히 항상 null이다.

**`breakdown` 단계 노출**

각 행에 `kind`가 붙는다: `free_window` → `benefit_free` → `progressive` → `daily_cap`
→ `benefit_rate` → `round_down`. 상한·감면·절사는 음수 금액이라 **`amt`를 모두 더하면 총액**이
된다. 이 불변식을 테스트로 고정했다. 여러 날이면 누진 행에 `date`가 붙는다.

- [x] `fee_windows`를 조사 데이터에서 읽어 실제 유료분만 계산
- [x] 평일·토요일·일요일·법정공휴일 그룹 조회
- [x] 실제 법정공휴일 달력 연결 — 조사 규칙 경로
- [x] 주차장별 토요일·공휴일 규칙 우선 적용
- [x] 24시간을 넘는 주차의 날짜별 누진·일 상한 재계산
- [x] 입차 당일 기준 일일권의 이용 범위와 구매 가능 조건 확정
- [x] 일일권 판매 여부·매진 정보가 없으면 가격만 안내하고 구매 가능으로 단정하지 않음 — `daily_pass_purchasable`은 항상 null
- [x] 후불과 일일권을 자동 합치지 않고 두 상품을 병기 — `apply_daily_pass_cap` 기본 False
- [x] 누진구간·무료구간·감면·100원 절사 순서가 보이는 `breakdown` 반환 — `kind` 로 단계를 구분하고 `amt` 합이 총액과 일치
- [x] 계산 불가 사유를 `null + reason`으로 반환하고 임의 추정 금지

### 5.3 카카오 OAuth — P1 후반

다른 기기에서도 설정을 동기화해야 할 때 추가한다.

11단계 구현 완료: `src/serve/auth.py`. 저장 정책이 이 모듈의 핵심이다.

- **액세스 토큰을 저장하지 않는다.** 코드를 토큰으로 바꿔 계정 식별자를 한 번 읽고 즉시 버린다.
  카카오 API를 대신 호출할 일이 없으니 들고 있을 이유가 없다. 암호화할 토큰 자체가 남지 않는다.
- **카카오 계정 식별자도 원본으로 두지 않는다.** 서버 페퍼로 HMAC 해시해서 넣는다.
  같은 사람을 다시 알아보는 데는 충분하고, DB가 새도 원본 ID는 복원되지 않는다.
- **세션 쿠키 값도 해시로만 저장한다.** httponly · samesite=lax · 운영에서 secure.
- `state`는 서버에 적어 두는 1회용이며 10분 만료다. 실패 사유는 사용자에게 자세히 말하지 않는다.
- 저장하는 설정은 감면 **코드**와 기본 주차시간뿐이다. 그 밖의 필드는 모델이 거부하고
  저장 직전에도 한 번 더 걸러낸다.

환경변수 `KAKAO_CLIENT_ID`(없으면 기존 REST 키) · `KAKAO_REDIRECT_URI` · `SESSION_PEPPER`가
없으면 기능을 켜지 않고 503으로 알린다. 반쯤 동작하지 않는다.

### 7.1 추천 결과의 실제 지도 — P0

추천 화면 상단에는 장식용 배경이 아니라 **실제 확대·이동 가능한 지도**를 둔다.

- 목적지는 별도 모양/색의 핀으로 표시한다.
- 추천 주차장은 카드 순위와 같은 번호 핀으로 표시한다.
- `추천순/요금 낮은순/도보 짧은순` 탭이 바뀌면 핀 번호도 현재 카드 순위와 함께 바뀐다.
- 지도 핀을 누르면 해당 카드를 펼치거나 그 카드로 스크롤하고, 카드를 누르면 지도 핀을 강조한다.
- 지도 이동 후에는 자동 재검색하지 않고 `이 지역 다시 검색` 버튼을 눌렀을 때만 목적지를 변경한다.
- 예측 불가 주차장은 핀을 숨기지 않고 상태를 구분한다. 출입 불가 후보는 기본 지도에서 숨기고
  사용자가 `제외된 주차장`을 펼쳤을 때만 별도 스타일로 표시한다.
- `확대`·`축소`·`내 위치`와 지도/목록 전환 또는 지도 높이 조절을 제공한다.

- [ ] 현재 좌표 투영식으로 그린 모형 지도를 실제 지도 SDK로 교체
- [ ] 목적지 핀과 순위 번호 주차장 핀 구현
- [ ] 핀↔카드 양방향 선택·스크롤·강조 동기화
- [ ] 정렬 탭 변경 시 핀 순위와 카드 순위를 함께 갱신
- [ ] 지도 로딩 실패 시 목록은 계속 사용할 수 있는 폴백 제공
- [ ] 모바일 실기기에서 핀 겹침, 지도 스크롤과 페이지 스크롤 충돌, 하단 카드 가림 확인

9단계 구현 완료: `web/src/api/`에 타입·클라이언트·표시 규칙을 두고 `App.tsx`가 실제 응답만 읽는다.

rolling-origin이라 폴링이 쌓이면 test 창이 저절로 밀리므로, 재실행 전에 인증 관문이
열렸는지 먼저 본다.

**⚠️ 주말 조건의 계측 약점을 발견했다.** `weekend_weeks`는 ISO 주 수를 센다. 그래서
서로 다른 주의 토요일 하나·일요일 하나도 "2회"로 잡힌다. 2026-09-20까지 데이터가 쌓이면
조건이 열리지만 그때 **온전한 주말(토·일 쌍)은 0회**다. 또 09-21·09-22에는 다시 1회로
닫힌다 — 창이 밀리며 오르내린다. 스크립트가 두 수치를 함께 찍으므로, 이 방식으로 인증하면
리포트에 그 사실을 반드시 적는다.

층화 평가(`src/analysis/a26_gate_stratified.py`): 예측 43.9만 행의 **73.2%가 게이트 허용
구간**이다. 대표 수치는 허용 구간만으로 낸다 — 차단 구간은 사용자에게 예측이 나가지 않으므로
합산하면 리포트가 실제 서비스와 달라진다.

| 지평선 | ML MAE | persistence | 개선 |
|---|---|---|---|
| 15분 | 2.23 | 2.31 | 3.2% |
| 30분 | 3.32 | 3.66 | 9.2% |
| 60분 | 4.92 | 5.96 | 17.4% |
| 120분 | 7.32 | 10.01 | 26.8% |

persistence에 지는 칸은 **세 개뿐이고 전부 주말 × 차단 구간**이다(MAE 0.45~2.32로 값 자체가
거의 안 움직이는 시간대). 서비스가 예측을 내보내지 않는 구간이라 대표 수치에 들어가지 않는다.

U11 구간 재평가(`scripts/reevaluate_intervals.py`): 배포 모델의 `interval_gate`는 **16칸 전부
닫혀 있다**. 즉 지금 UI에 p10~p90이 하나도 나가지 않는다 — 통과한 구간만 표시한다는 조건은
지켜지고 있다. 열 수 있는 칸은 6개이며 **전부 운영시간 외**다.

**운영시간 중 8칸은 전부 미달이다**(커버리지 0.635~0.765로 목표 0.77 미만 = 구간이 좁아
거짓 확신을 준다). 사람이 실제로 주차하는 시간대에 구간이 가장 못 믿을 만하다는 뜻이라,
닫아 둔 현재 상태가 옳다. 게이트 변경은 학습·보정과 함께 `u11_evaluate`가 정한다.

정확도 게이트(`src/serve/accuracy_gate.py`, `scripts/build_accuracy_gate.py`):
지평선을 통째로 막던 것을 **주차장 × 지평선**으로 쪼갰다. 240분은 전체 합격률 73%로
막혀 있었지만, 실제로는 **36곳이 MAE 5.4로 잘 맞고 18곳이 14.8로 끌어내린** 것이었다.
못 맞히는 칸만 빼니 240·360분을 열 수 있다.

인증은 시험 기간 전·후반 **양쪽 모두** 합격해야 한다. 성적 좋은 주차장만 골라 넣으면
그 성적이 선택 편향이 되기 때문이다. 재현율은 15~180분 95~100%, 240분 88%, 360분 78%다.

`prediction_availability.csv`(값이 움직이는가)와 `prediction_accuracy.csv`(맞히는가)는
목적이 다르다. 둘 다 통과해야 예측이 나가고, 어느 쪽에 막히든 위치·요금·실시간은 그대로다.

A27 실험(`src/analysis/a27_continuous_horizon.py`): 지평선을 피처로 넣으면 5분 단위
연속 예측이 가능하지만 전 구간에서 이득은 아니다. 20~45분은 연속이 2.4~6.3% 낫고,
50분 이상은 격자가 낫다. **15분 이내는 모델이 persistence에 진다(3일 모두 재현)** —
지금 15분 모델로 반올림해 더 나쁜 답을 내보내고 있으므로 고칠 대상이다.
