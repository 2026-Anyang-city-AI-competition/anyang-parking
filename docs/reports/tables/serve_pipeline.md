## ★ TMAP — ✅ 해결됨 (2026-09-06)

원인은 **앱에 API 상품이 하나도 붙어 있지 않은 것**이었다. appKey 자체는 정상이었다.
앱 상세 화면의 `AccessKey 정보` 가 "AccessKey가 있는 상품이 없습니다" 였고,
게이트웨이가 라우팅 전에 막아 **보행자·자동차·POI·지오코딩 6개 엔드포인트가 전부**
`403 INVALID_API_KEY` 였다(`category: "gw"`).

「경로안내」 상품을 앱에 붙이자 **키 재발급 없이 그대로 통했다.**

**쿼터: 경로안내 그룹 Free 1,000건/일** — 자동차·보행자·타임머신·이미지·화물차가 **공유**한다.
후보 N곳이면 N회이므로 **캐시가 필수다**(아래 3번).

## 1. TMAP 실응답 원형 — ✅ 확정

```
POST https://apis.openapi.sk.com/tmap/routes/pedestrian?version=1&format=json
Header  appKey: {TMAP_APP_KEY} · Content-Type: application/json
Body    startX/startY (주차장) · endX/endY (목적지)   ★ X=경도, Y=위도
        startName/endName · reqCoordType/resCoordType="WGS84GEO" · searchOption="0"
```

**실응답 (HTTP 200 · 10,142B)**
```
최상위 키: ['type', 'features']       features 20개 (경로 구간별)
features[0] 키: ['type', 'geometry', 'properties']
features[0].properties:
  {"totalDistance": 236, "totalTime": 271, "index": 0, "pointIndex": 0,
   "name": "", "description": "보행자도로를 따라 1m 이동", "facilityType": "17",
   "turnType": 200, "pointType": "SP", ...}
```

**확정 경로** — 공식 예제와 일치했다
```
features[0].properties.totalDistance   (m)
features[0].properties.totalTime       (초)
```
전체 거리·시간은 **첫 feature 에만** 들어 있다. 나머지 19개는 구간 안내다.
예상 필드가 없으면 실제 키 목록을 찍고 `None` 을 돌려주므로 틀린 필드로 조용히 넘어가지 않는다.

### ★ 여기서 잡은 버그 — 응답에 제어문자가 섞인다

22건 중 1건(4.5%)이 `JSONDecodeError: Invalid control character at char 10884` 로
죽어 **조용히 폴백에 떨어졌다.** `r.json()` 은 strict 파서다.
`json.loads(r.text, strict=False)` 로 재파싱하도록 고쳤고, 이후 **24/24 성공·폴백 0**.

일방통행·좌회전 금지가 없기 때문이다. 「도보 축을 차 거리로 대신하면 안 된다」는

## 3. 캐시 — ✅ 검증 완료 (★ 버그 1건 수정)

`data/interim/walk_cache.sqlite` · PK `(parking_id, 격자위도, 격자경도)`

**실호출로 검증했다.** 같은 질의를 반복하면 TMAP 을 다시 부르지 않는다.

```
1회차   TMAP 5회 · 캐시적중 0 · 폴백 0
2회차   TMAP 0회 · 캐시적중 5 · 폴백 0      ← 전건 캐시
주입값 단독 확인: source=cache · TMAP 호출 0 · 적중 카운트 +1
```

**Free 1,000건/일** 기준으로 캐시가 없으면 후보 8곳 검색 125회면 소진된다.
주차장 좌표가 고정이라 실사용에서는 적중률이 훨씬 높다.

**★ 격자 스냅이 전혀 작동하지 않는 버그를 잡았다.**
`dlon` 을 **원본 위도**로 계산하고 있어서 점마다 셀 크기가 미세하게 달라졌다.

| | 100m 반경 200개 좌표 → 셀 수 |
|---|---|
| 수정 전 | **200개** (스냅 무효) |
| 수정 후 | **9개** — 적중률 **22배** |

`dlon` 을 **스냅된 위도**로 계산하도록 고쳤다.
⚠️ 격자 경계를 걸친 두 점은 30m 차이여도 다른 셀이 된다. 구조상 정상이다.

호출 카운터는 `walking.CALLS = {"tmap", "cache_hit", "fallback"}` 로 노출한다.

## 4. 후보 선정 — ✅ 검증 완료

반경 1km → 5곳 미만이면 2km → 3km. **3km 가 상한.**

| 목적지 | 500m | 1km | 2km | 3km | 선택 반경 | 후보 | 최근접 |
|---|---:|---:|---:|---:|---:|---:|---|
| 안양역 | 5 | 13 | 32 | 46 | 1000m | 13 | 안양역2노상 118m |
| 인덕원역 | 7 | 11 | 26 | 34 | 1000m | 11 | 인덕원2노상 2m |
| 안양시청 | 4 | 8 | 35 | 58 | 1000m | 8 | 평촌지하 242m |
| 평촌역 | 1 | 7 | 34 | 52 | 1000m | 7 | 평촌역노상 270m |
| 범계역 | 2 | 7 | 36 | 63 | 1000m | 7 | 범계역노상 285m |
| **석수역** | 1 | **1** | **6** | 11 | **2000m** | **6** | 석수역좌우측노상 217m |

지시서의 실측 표와 일치한다. 인덕원역 500m(7 vs 6)·석수역 2km(6 vs 5)만 1곳 차이인데
목적지 좌표를 카카오 키워드 검색으로 잡아서 생긴 차이로 보인다.

**석수역은 2km 에서 6곳이 되어 3km 까지 가지 않는다.** 반경 확장이 실제로 동작한다.
라벨 없는 표준데이터 곳은 `unlabeled` 로 따로 담아 **순위에 넣지 않는다.**

## ★ 요금 계산기에서 잡은 버그 1건

**`00:00~00:00` 을 24시간 운영으로 읽고 있었다.** 실제로는 **미운영**이다.

```
주말 start=end        58곳 (그중 00:00~00:00 이 57곳)   ← 주말 미운영
주말 00:00~24:00       7곳                             ← 진짜 24시간
평일 start=end         2곳
```

수정 전에는 주말 요금이 24시간 누진으로 계산돼 **일 상한 25,000 에 걸리는 곳이 속출**했다.
`start == end` 는 미운영(과금 0)으로 처리한다. 과소청구가 과다청구보다 안전하다.
`00:00~24:00` 은 그대로 24시간으로 읽는다. 단위 테스트 3건 추가(총 36건 통과).

⚠️ 인덕원환승(평일 `00:00~00:00`)은 실제로 24시간 운영일 수 있다. 89곳 중 1곳뿐이라
9/5 실측 때 확인하면 좋다.

## 설계 반영 확인

| 지시 | 반영 |
|---|---|
| ② 축은 도보 시간 | `by_walk` 정렬이 `walk_min` 기준. 차 거리 안 씀 |
| 차 ETA 와 도보를 섞지 않음 | `arrive = depart + drive_s` — 도보를 더하지 않는다. 예측 시점은 주차장 도착 |
| `drive_min`/`walk_min` 분리 | 카드에 따로 담고 `total_min` 은 표시용으로만 |
| 도보 15분 초과 경고 | `walk_far_warning` |
| 요금 병기 | `fare_payg` + `fare_daily_pass`, `min()` 자동 적용 없음 |
| 미래운행은 단건 | `depart_in_min>0` 이면 목적지 ETA 하나를 전 후보에 공통 적용 |
| 폴백은 강등 제외 | `demote()` 가 `estimated` 인 항목을 건너뛴다 |
| 반경 3km 상한 | `RADII = (1000, 2000, 3000)` |
